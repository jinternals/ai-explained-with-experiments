Cross-Encoder Re-Ranking

Search finds a hundred candidates in milliseconds. A cross-encoder then reads each one next to the question and puts them in a new order. This post tests that second step on {{d:total.queries|int}} real questions and measures what it costs.

Follows Reciprocal Rank Fusion, Without the Scary Math. Every number on this page was printed by the Java lab in section 11.

Short version. Meaning search turns the question and each document into lists of numbers separately, then compares the lists. A cross-encoder reads the question and one document together, as one piece of text, and gives a single relevance score. That is more careful and much slower, so it is only used on the top results from a fast search.

Where this fits

The previous post merged two searchers. Keyword search (BM25) looks for the question's exact words. Meaning search looks for documents that mean the same thing. Reciprocal Rank Fusion (RRF) merges their two ranked lists into one by adding up points for each document's position.

That post ended by noting that RRF works well as a first step in systems that re-sort the top results with a slower, smarter model afterwards. The slower, smarter model is usually a cross-encoder, and the re-sorting step is called re-ranking. This post tests it on the same data, with the same search engine, and the same way of scoring.

How meaning search compares text

Meaning search uses a model called a bi-encoder. Ours is all-MiniLM-L6-v2. It reads one piece of text on its own and turns it into a list of 384 numbers, called an embedding. Texts that mean similar things get similar lists.

The question and the document are read separately, at different times:

  • Ahead of timeEvery document is turned into its 384 numbers once, when it is added to the search engine. For NFCorpus that is 3,633 documents, done once.
  • At search timeOnly the question is turned into 384 numbers. The search engine then finds the documents whose numbers are closest, using a measure called cosine similarity: 1 means pointing the same way, 0 means unrelated.

This is why meaning search is fast. On our setup, turning a question into numbers took {{b:timing.embed_query_median_ms|1}} ms, and finding the 100 closest documents took {{b:timing.vector_search_top100_median_ms|1}} ms. (Medians over {{b:timing.queries_timed|int}} NFCorpus questions.)

The price of that speed is that the model never sees the question and the document at the same time. Each is reduced to 384 numbers without knowing what it will be compared with, so details that matter only for this particular question can be lost.

How a cross-encoder compares text

A cross-encoder takes the question and one document, joins them into a single piece of text, and reads them together. Inside the model, every word of the question can look at every word of the document, and the other way round. At the end it outputs one number: how well this document answers this question.

Our cross-encoder is cross-encoder/ms-marco-MiniLM-L6-v2. It is small: 6 layers, trained on MS MARCO, a large set of real Bing search questions with passages that people marked as answering them. It reads at most 512 tokens per pair, so long documents get cut off.

Its output is a single number with no fixed range. In the worked example below it runs from {{e:documents.8.cross_encoder_score|1}} to {{e:documents.4.cross_encoder_score|1}}. Higher means more relevant, and only the order matters. You can squash it into 0 to 1 with a sigmoid function if you want something that looks like a probability, but the ranking stays the same.

Why it only re-ranks a short list

Nothing can be prepared ahead of time. To rank a whole collection with a cross-encoder, you would run it once for every document, for every question.

On our setup ({{b:cpus|int}} CPU cores in Docker), re-ranking 100 documents for one question took {{b:timing.cross_encoder_rerank.100.median_ms|0}} ms, about {{b:timing.cross_encoder_rerank.100.pairs_per_second|int}} pairs per second. At that rate, scoring all {{b:timing.whole_corpus_documents|int}} NFCorpus documents for one question would take about {{b:timing.whole_corpus_estimated_seconds_per_query|0}} seconds. FiQA has 57,638 documents. (The whole-collection time is worked out from the measured rate, not run.)

So real systems split the work in two:

  • Stage 1: find candidates, fastKeyword search, meaning search, or RRF of both, returns the top 100 or so. This takes milliseconds because the documents were prepared ahead of time.
  • Stage 2: re-rank, carefullyThe cross-encoder scores only those candidates and sorts them by its score. The user sees the new top 10.

For scale, the model card lists 1,800 documents per second for this model, measured on an NVIDIA V100 GPU. A GPU would make stage 2 much faster. The two-stage split would still be needed for large collections.

The worked example

Here is the question from Step 3 of the RRF post: "{{e:query|text}}". We take the same top-5 lists from keyword search and meaning search, merge them with RRF, and then let the cross-encoder re-rank the merged list. We also scored the two relevant papers that neither searcher found. (out/example.json)

The cross-encoder made this question worse. RRF had the one relevant paper it found in 1st place. The cross-encoder moved it to {{e:documents.0.cross_encoder_rank|int}}th and put "Possible neurologic effects of aspartame" first. nDCG@10 dropped from {{e:ndcg@10.rrf|3}} to {{e:ndcg@10.rrf_then_cross_encoder|3}}.

Read the question again, though. "Neurologic effects of aspartame", a widely used sweetener, is a reasonable answer to "neurobiology of artificial sweeteners". The disagreement comes from the labels. NFCorpus marks a paper relevant when a NutritionFacts.org article cites it, not when a person judged it a good answer to this exact question.

Three more things this small example shows:

  • It separates near-misses more clearly.Cosine similarity rated the paper on cherry phenolics ({{e:documents.7.cosine|2}}) as close to the question as the relevant sucrose paper ({{e:documents.0.cosine|2}}). The cross-encoder split them clearly: {{e:documents.7.cross_encoder_score|1}} against {{e:documents.0.cross_encoder_score|1}}.
  • It can only reorder what it is given.The two relevant papers the searchers missed got the two lowest scores of all. The cross-encoder also judged them poor answers to this question, another sign of how loosely NFCorpus's labels match the wording of its questions.
  • It is not free.Scoring these {{e:pairs_scored|int}} pairs took {{e:milliseconds|0}} ms, after a warm-up call.

One question tells us very little, and this one was picked because it teaches well. The next section runs the same test on every question.

How many results to re-rank

Re-ranking more candidates gives the cross-encoder more chances to find something good, and costs more time. We re-ranked the top 10, 20, 50 and 100 of the RRF list. Re-ranking only the top 10 cannot bring in anything new; it can only change the order inside the top 10.

For RRF, re-ranking the top 20 did better than re-ranking the top 100 on all three datasets. It also costs about a sixth of the time: {{b:timing.cross_encoder_rerank.20.median_ms|0}} ms instead of {{b:timing.cross_encoder_rerank.100.median_ms|0}} ms per question.

The likely reason going deeper hurt: the extra candidates are mostly not relevant, and each one is another chance for the cross-encoder to lift a wrong document into the top 10. Keyword search behaved differently. On NFCorpus and FiQA it kept improving all the way to 100, which suggests its relevant documents often sit further down its list.

On NFCorpus, RRF's top 100 holds only a third of the relevant documents, so two thirds are out of reach before re-ranking starts. Even so, putting that top 100 in perfect order would reach {{b:datasets.nfcorpus.perfect_rerank_ndcg@10.rrf|3}}, and the cross-encoder reached {{b:datasets.nfcorpus.ndcg@10.rrf.100|3}}. The same gap shows on SciFact, where the top 100 already holds {{b:datasets.scifact.recall@100.rrf|pct}} of the relevant documents.

So on these datasets the cross-encoder's own judgement is the bigger limit, not the candidate list. It is a small 6-layer model trained on web search questions, and here it is judging nutrition research, scientific claims and personal finance. Larger re-rankers, or ones trained on data closer to these topics, are the usual next step.

In code

With LangChain4j, a cross-encoder is a ScoringModel. You give it the question and the candidate texts, and you get one score per candidate back. This is the core of the lab's Reranker.java:

var model = new OnnxScoringModel("model.onnx", "tokenizer.json");   // ms-marco-MiniLM-L6-v2

List<TextSegment> texts = candidates.stream()
        .map(doc -> TextSegment.from(doc.title() + " " + doc.text()))
        .toList();
List<Double> scores = model.scoreAll(texts, question).content();

// Sort the candidates by score, highest first. That is the whole re-ranking step.

The model runs inside the Java process with ONNX Runtime, so no Python or separate server is needed. Inside OpenSearch, the same step can be done with a rerank processor in a search pipeline, using a cross-encoder model deployed through ML Commons.

Summary

  1. Meaning search reads the question and each document separately.Documents become 384 numbers ahead of time, so search takes milliseconds, but the model never sees the question and the document together. (Section 02)
  2. A cross-encoder reads them together.It joins the question and one document and outputs one score. It is more careful, and it has to run again for every pair. (Section 03)
  3. So it only re-ranks a short list.Re-ranking 100 candidates took {{b:timing.cross_encoder_rerank.100.median_ms|0}} ms per question on CPU. Scoring all of NFCorpus would take about {{b:timing.whole_corpus_estimated_seconds_per_query|0}} seconds per question. (Section 04)
  4. It can disagree with the labels.On the worked example it moved the one labelled paper from 1st to {{e:documents.0.cross_encoder_rank|int}}th, in favour of a paper that arguably fits the question better. (Section 05)
  5. Across all questions:re-ranking RRF's top 100 changed nDCG@10 by {{d:gain_pct.nfcorpus.rrf|signed0}}% on NFCorpus, {{d:gain_pct.scifact.rrf|signed0}}% on SciFact and {{d:gain_pct.fiqa.rrf|signed0}}% on FiQA. (Sections 06 and 07)
  6. Re-rank the top 20, not the top 100.For RRF, the top 20 did better on all three datasets and took about a sixth of the time. (Section 07)
  7. It cannot find what stage 1 missed.RRF's top 100 held {{b:datasets.nfcorpus.recall@100.rrf|pct}} of the relevant NFCorpus documents. Even within those, a perfect order would score far higher than the cross-encoder did. (Section 08)

Run it yourself

The lab is Java 21 with OpenSearch in Docker, the same setup as the RRF lab.

$ docker compose run --rm --build lab example     # section 05, about a minute
$ docker compose run --rm --build lab benchmark   # sections 04 and 06–09
$ docker compose down
$ python3 blog/build_page.py                      # rebuild this page from out/*.json
