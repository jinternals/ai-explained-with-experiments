Defeating Nondeterminism, on a Mac

Ask a model the same question at temperature 0 and you can still get two different answers. This post finds out why, one experiment at a time, on a MacBook.

Based on Defeating Nondeterminism in LLM Inference by Horace He and Thinking Machines Lab, September 2025. Numbers tagged ran on Mac were printed by the scripts in section 11, run on an M4 Pro. Numbers tagged paper are quoted from the article.

Short version. A server groups your request with other people's requests into one batch. How many requests are in that batch depends on traffic. The GPU picks a different way of adding numbers depending on the batch size, and a different order of adding gives slightly different rounding. Usually that changes nothing. But every so often two candidate words score almost the same, and then the rounding decides which one you get. In our runs that happened after 110 to 232 tokens.

What the Mac showed. The same calculation repeated 1,000 times gave identical results. The same row gave 3 different results depending on batch size. A real model asked the same question at temperature 0 gave 8 different answers across 11 batch sizes. With the batch size held fixed it gave 4 of 4 identical answers.

Temperature 0 should mean one answer

A language model writes one token at a time. A token is a word or a piece of a word: " particle", " quantum", " Feyn", "man". At each step the model gives every token in its vocabulary a score, called a logit. Higher score means "more likely to come next".

Temperature controls how the next token is picked from those scores. At a high temperature the model samples, so a lower-scored token sometimes wins. At temperature 0 there is no sampling at all. The model takes the highest score every time. This is also called greedy decoding.

So at temperature 0, the same prompt with the same model should give the same text every time. The article tested this. paper

  • SetupQwen3-235B, prompt "Tell me about Richard Feynman", run 1,000 times, 1,000 tokens each, temperature 0.
  • Result80 different completions. The most common one appeared 78 times.
  • Where it splitAll 1,000 runs agreed for the first 102 tokens, up to "Feynman was born on May 11, 1918, in". At token 103, 992 runs wrote "Queens, New York" and 8 wrote "New York City".

To see why, we first need to know what a batch is.

What a batch is, and why servers use one

A model is mostly a big pile of numbers called weights. The small model used in this post, Qwen2.5-0.5B, has about 500 million of them, roughly 1 GB. To write one token, the GPU has to read all of those weights from memory and do arithmetic with them.

Reading 1 GB takes time. The arithmetic for one request is small by comparison, so the GPU spends most of each step waiting for weights to arrive. A batch fixes that. The server stacks several users' requests into one table, one row per request, and runs them through the model together. The weights are read once per step and used for every row.

Here is what that looks like on the M4 Pro. Same model, same prompt, 300 tokens per request. ran on Mac

You don't choose the batch. If 3 other people send a request at the same moment as you, your request runs in a batch of 4. A second later it might be a batch of 50. On a real server the batch size changes all the time, and nobody can predict it.

The rows in a batch do not mix. Row 7 is only ever multiplied by the weights, never by row 3. So on paper your answer cannot depend on who else is in the batch. Section 06 shows that on a real GPU it does.

The rest of this post traces how that happens, starting from the arithmetic.

Computers round after every addition

A computer stores every number in a fixed number of bits. A fixed number of bits can only hold a fixed set of values. When the exact result of an addition is not one of those values, the computer stores the nearest one it has. That is rounding. It happens after every single addition, because every result goes back into a slot of the same size.

Picture a calculator whose screen shows only 3 significant digits. 1230 + 23.4 is exactly 1253.4. The screen can show 1250 or 1260, but not 1253.4, so it shows 1250. The addition was done correctly. The 3.4 was lost when the result was fitted onto the screen. The article uses this same example. paper

The number formats a computer uses are called floating point. They work like scientific notation with a fixed number of digits: a few significant digits, plus a note of where the decimal point goes. Because the number of digits is fixed, the gap between neighbouring storable numbers grows as the numbers get bigger. Models use two small 16-bit formats to save memory, float16 and bfloat16 (bf16). A normal Python number uses 64 bits. ran on Mac

Near 21, bf16 can store 20.875, 21.0 and 21.125, and nothing in between. Keep that row in mind for section 08. Near 1e20, even a 64-bit number can only step in jumps of 16,384.

Keeping every digit is not practical. The exact sum of many numbers can need any number of digits, and a chip's circuits have a fixed width. Fewer bits also means less memory to move and more numbers handled per second, which is why models use 16-bit formats. GPUs usually add the products up in 32 bits even when the weights are stored in 16. That makes the gaps much smaller, but they never reach zero.

Here is the smallest example that shows the problem, in real float16. Above 2048 the gap is 2, so float16 can only store even numbers. 2049 does not exist, so 2048 + 1 rounds back to 2048. (2049 is exactly halfway between 2048 and 2050. Ties go to the neighbour whose last bit is 0, which is 2048.) ran on Mac

Same five numbers, same float16, two different answers. In one pass, each 1 meets the big number alone and gets rounded away. Split into halves, the three 1s get added to each other first, make 3, and survive. The order of additions decides what gets rounded away.

The article's own example shows the same effect in two lines. ran on Mac

>>> (0.1 + 1e20) - 1e20
0.0
>>> 0.1 + (1e20 - 1e20)
0.10000000149011612

This ran in 32-bit floats, where the gap near 1e20 is about 8.8 trillion. In the first line, 1e20 + 0.1 is nowhere near the next storable number, so it is stored as exactly 1e20, and subtracting 1e20 leaves 0. In the second line, 1e20 − 1e20 is 0 first, and 0 + 0.1 is fine. (0.10000000149 is the nearest 32-bit value to 0.1.)

The article then takes 8 numbers whose true total is exactly 0, shuffles them, adds them up, and repeats 10,000 times. The GPU decides the order

A model does very little except add up long lists of products. Adding up a list into one number is called a reduction. A GPU has thousands of small cores, so it never adds a long list one number at a time. It gives pieces of the list to different cores, adds each piece, then adds the piece totals. The code that decides how to cut up the work is called a kernel.

Different ways of cutting up the list are different orders of addition. We summed the same 1,048,576 random numbers five ways, all in 32-bit floats. ran on Mac

Running the same thing twice gives the same bits

The explanation you usually hear goes like this. The GPU runs thousands of threads at once, they finish in a random order, so the additions happen in a random order and the result wobbles. If that were true, repeating the exact same calculation would give different results.

So we repeated a matrix multiplication 1,000 times. ran on Mac

>>> A, B = random bf16 matrices, 2048 × 2048
>>> ref = A @ B
>>> largest difference from ref, over 1,000 repeats
0.0

Identical every time. The article found the same on an NVIDIA GPU. paper

Random order needs a specific ingredient called an atomic add. That is when many threads add into the same memory slot and whichever arrives first goes first. The article notes that the forward pass of an LLM, the part that produces the next token, usually has no atomic adds at all. Each core owns its own piece of the output and adds its numbers in a fixed order. Same inputs and same sizes give the same bits, every time.

So the randomness comes from somewhere else

The arithmetic repeats exactly. What differs between your two requests is the size of the batch they ran in.

Batch size changes the order

Your request is one row of 4,096 numbers. Multiplying it by a 4,096 × 4,096 weight matrix gives 4,096 outputs. Each output is a sum of 4,096 products, and every one of those products is one of your numbers times one weight. Another user's row never enters any of your sums.

So your 4,096 outputs should come out exactly the same whether you run alone or share the batch with 511 other people. A kernel that keeps this promise is called batch invariant. The article's claim is that most kernels don't keep it.

The article's test: multiply the first row on its own, then multiply the whole batch and take its first row. The two should be identical. ran on Mac

>>> a = linspace(-1000, 1000).reshape(2048, 4096)
>>> b = linspace(-1000, 1000).reshape(4096, 4096)
>>> largest | a[:1] @ b  −  (a @ b)[:1] |
1448.97    (the values are around 722,042, so about 0.2% off)

The article got 1669.25 on an NVIDIA GPU. paper The exact size depends on the hardware. It is not zero on either.

Why the batch changes the result

Because the kernel changes its plan. A GPU is fast only when all of its cores have work. The GPU in this M4 Pro has 20 cores, and each core runs many groups of threads at once. So a matmul kernel cuts the output into small blocks called tiles, 16 rows by 16 columns in MLX, and hands out one tile per thread group. Each group adds up the long sums for the 256 outputs in its tile.

A row of 4,096 outputs is 256 tiles wide (4,096 ÷ 16). One tile is 16 rows tall. So the number of tiles grows with the batch: ran on Mac

With few tiles, each thread group would have to walk through a sum of 4,096 products on its own while the rest of the GPU waits. So when the output is small and the sums are long, MLX uses split-K. It cuts every sum into two halves of 2,048, gives each half to a different thread group, and adds the two half-totals at the end. That doubles the number of jobs. On Pro and Max chips it does this while there are at most 2,048 tiles. 128 rows is exactly 8 tiles tall, which makes 2,048 tiles. 129 rows needs a 9th tile row, the count jumps to 2,304, and MLX switches to the normal tiled plan. That is where the 129 comes from.

Think of it as adding up 4,096 receipts. With plenty of work to go round, one clerk adds the whole pile. When the office is quiet, each pile goes to two clerks who add half each, and then someone adds their two totals. Both methods are correct, but section 03 showed that the order of adding changes what gets rounded away.

Split-K is the float16 example from section 03 at full size. Adding in two halves and then combining rounds at different moments than adding in one pass.

Inside a plan, the result does not move. Batch 2, 8 and 128 all give the same numbers, and so do 129 and 512. It changes only when the plan changes. We then checked every batch size from 1 to 1,024, one at a time. The row changed at exactly two places, 2 and 129. ran on Mac

More precision does not fix it. With 32 bits almost every output changes, because there are so many digits that nearly every sum lands on a slightly different last digit. bf16 keeps so few digits that most differences round away, and only 1 output of 4,096 changed. The largest change was 0.001, in float16. Section 08 shows that a change this small can still change a word.

What it costs to avoid

The simplest way to get batch invariance is to always use one plan. With 2 users, that means padding the batch with 127 empty rows so MLX takes the 129-row plan. Your row then comes out identical whatever the real batch size. It also took 2.5 to 3.1 times longer than the 2-row split-K plan in three runs (for example 0.40 ms versus 1.17 ms), because the GPU now multiplies 129 rows instead of 2. ran on Mac The article's batch-invariant kernels also give up some speed, mostly at small batches. paper

Three places a model adds things up

A transformer model repeats the same block of steps many times (24 blocks in Qwen2.5-0.5B). Three kinds of step inside it add up long lists, so those are the three places where batch size can matter.

Matrix multiplication (matmul)
Each output number is one row of the input times one column of the weights: 4,096 products added together. Most of a model's work is this.
RMSNorm
Rescales each row so its numbers stay in a sensible range. To do that it adds up the squares of every number in the row.
Attention
Lets the new token look back at every earlier token. It scores the new token against each earlier one and takes a weighted sum over all of them. The earlier tokens' data is kept in memory so it isn't recomputed each step. That store is the KV cache, and it grows by one entry per token.

We tested each one alone versus inside a batch. ran on Mac

The article fixes each one with the same rule: choose one plan for adding up and use it at every batch size. paper

  • RMSNormOne core per row, and that core adds the whole row itself. More rows just means more cores busy. The kernel must not start splitting rows when the batch is small, even though that leaves cores idle. Small batches run a little slower.
  • MatmulCompile one kernel setup and use it for every size, with no split-K for small batches. This ran about 20% slower than NVIDIA's cuBLAS library, most of it at very small batches.
  • AttentionWhile generating, each user adds only one new token per step, so kernels cut the KV cache into pieces to keep the GPU busy. Normally the number of pieces depends on the batch. The article fixes the size of each piece instead. A cache of 1,000 tokens is always cut into 256 + 256 + 256 + 232, however many requests are running.

A tie decides the word

A change of 0.001 does nothing most of the time. The highest-scoring token usually leads by a wide margin, and a tiny nudge does not change the winner. It matters only when two tokens are nearly tied.

The batch-size pattern is not as clean as the three regions in section 06. The model has many layers, and they run matmuls of different shapes. Some of those shapes take other routes in MLX. For example, MLX's source sends 2 to 15 rows through a separate "wide" matrix-vector kernel in bf16 and float16. Every layer's small difference feeds into the next layer.

After one token differs, every later token is predicted from different text, so the two answers drift further apart. It is the same kind of split as the article's "Queens, New York" versus "New York City".

Keep the batch shape fixed

We did not write new kernels. We used the simplest fix the diagnosis suggests: always run the GPU with exactly 32 rows. Real requests fill the first rows and filler rows fill the rest. The GPU then always sees the same shapes, picks the same plans, and adds in the same order, whatever the traffic. ran on Mac

Training needs the same numbers twice

One place this matters a lot is reinforcement learning (RL), where a model improves by trying answers and being scored. Two separate systems are involved. The sampler generates answers quickly, usually with an inference server that batches. The trainer then recomputes the probability of each chosen token and nudges the model toward the better answers.

The trainer assumes its probabilities match the ones the sampler used. If the two ran at different batch sizes, they don't quite match, so the model is learning from slightly different behaviour than it produced. The article measured the gap with KL divergence, a single number for how far apart two sets of probabilities are. 0 means identical. paper

  • No correctionThe gap spikes around training step 318 and the reward collapses.
  • A standard correctionImportance weighting, which reweights each sample by how different the two probabilities are. The gap stays around 0.001 with occasional spikes, and training stays stable.
  • Batch-invariant kernelsSampler and trainer produce the same bits. The gap is exactly 0 for the whole run.

Summary

  1. Temperature 0 does not guarantee one answer.The article ran a large model 1,000 times on one prompt and got 80 different answers. On the Mac, a 0.5B model gave 8 different answers across 11 batch sizes. (Section 01)
  2. Servers batch requests, and you don't choose your batch.Reading the weights once for many users is far cheaper: 32 users took 4.0 s together instead of 55 s one after another. How many users share your batch depends on traffic at that moment. (Section 02)
  3. Computers round after every addition, so order matters.Numbers live in a fixed number of bits, and the gaps between storable values grow with size. In float16, 2048 + 1 + 1 + 1 + 1 is 2048 added left to right and 2052 added in two halves. (Sections 03 and 04)
  4. Random GPU timing is not the cause.The same calculation repeated 1,000 times gave identical bits. The forward pass of a model has no atomic adds, so each run adds in the same order. (Section 05)
  5. Batch size changes the plan, and the plan changes the order.With few rows, MLX cuts each sum in two to keep the GPU busy (split-K). On the M4 Pro that happens from 2 to 128 rows, and a different plan runs at 1 row and from 129 up. Your row's result changes at each switch. Matmul and attention do this. RMSNorm did not. (Sections 06 and 07)
  6. A near-tie turns rounding into a different word.After 203 tokens, " particle" and " quantum" both scored exactly 21.0 when the request ran alone. In a batch of 2, " quantum" scored 21.125 and won, and the rest of the answer followed from there. (Section 08)
  7. Use one plan at every batch size.Padding every batch to 32 rows gave 4 of 4 identical answers, at 2.4 times the time for a single request. The article's batch-invariant kernels made all 1,000 answers identical, at 42 s instead of 26 s. (Section 09)
  8. It matters most for training.In reinforcement learning, the system that writes answers and the system that learns from them must compute the same numbers. With batch-invariant kernels the gap between them was exactly 0. (Section 10)
