BM25, Without the Scary Math

Keyword search gave one paper a score of 28.64. This post rebuilds that number one word at a time, shows what BM25's two settings do, and tests what changes results on 1,271 real questions.

Every number on this page was printed by the Java lab in section 11, unless it says it was worked out from the formula.

Short version. BM25 scores a document by adding up points for each word of the question that the document contains. Rare words earn more points than common ones. Using a word again earns a little more each time, but less and less. And a long document gets a small penalty, so it can't win only because it contains more words.

What we measured. Across 42 combinations of BM25's two settings, k1 and b, the best one beat OpenSearch's defaults by at most 0.005 nDCG@10 on any of the three datasets. Only extreme settings did real damage. Reducing words to their stem ("sweeteners" becomes "sweeten") mattered more: +0.021 on NFCorpus, +0.034 on SciFact and +0.015 on FiQA. With stemming and the BEIR paper's settings, we reproduce the paper's BM25 scores for NFCorpus and FiQA to three decimals.

What keyword search does

You type a question. The search engine has thousands of documents and has to decide which ones to show first. Keyword search does this by looking for documents that contain the words of the question, giving each one a score, and listing the highest scores first.

The standard scoring method for keyword search is BM25, short for "Best Match 25". It is the default in OpenSearch, Elasticsearch and Lucene. This post takes one real BM25 score apart and rebuilds it word by word.

The example comes from NFCorpus, a public test set of 3,633 medical research papers with real questions. We loaded it into OpenSearch and searched for "Neurobiology of Artificial Sweeteners". The top result was "The potential toxicity of artificial sweeteners.", with a score of 28.64. OpenSearch can explain exactly how it reached that number, and the rest of this post follows that explanation.

Three ideas

BM25 is built on three ideas:

  • Rare words count more.A document containing "sweeteners" tells you much more than one containing "of", because almost every document contains "of".
  • Repeating a word helps, less each time.A document that says "sweeteners" four times is probably more about sweeteners than one that says it once, but not four times more. The setting k1 controls how fast the extra credit runs out.
  • Long documents get a small penalty.A long document contains more words because it is long, so it would win too often. The setting b controls how strongly length is taken into account.

Written as a formula, the first idea becomes IDF (inverse document frequency) and the other two become TF (term frequency). For every word of the question that the document contains, BM25 multiplies IDF by TF, then adds up the results:

score = Σ IDF × TF

Σ means "add this up for every word of the question that appears in the document".

IDF = ln ( 1 + N − n + 0.5n + 0.5 )
TF = freq × (k1 + 1)freq + k1 × ( 1 − b + b × lengthavg length )
N
how many documents there are (3,633 in NFCorpus)
n
how many of them contain the word
freq
how many times the word appears in this document
length
how many terms this document has; avg length is the average over all documents
k1
how quickly repeats stop adding more (OpenSearch's default: 1.2)
b
how much document length counts, from 0 (not at all) to 1 (fully); default 0.75
ln
the natural logarithm: it grows fast for small numbers and slowly for large ones

The next sections go through IDF and TF with the real numbers behind the 28.64.

First, the text is split into words

Before any scoring, OpenSearch runs every document and every question through an analyzer, which turns text into the list of words, called terms, that it will match. OpenSearch's default is the standard analyzer: split on spaces and punctuation, and lowercase. The english analyzer also drops very common words, called stop words, and cuts words down to their stem, so that "sweetener" and "sweeteners" become the same term. With the standard analyzer, a document that says "sweetener" does not match the question's "sweeteners" at all. With the english analyzer both become "sweeten". Section 09 shows how much that alone changes.

IDF: rare words count more

IDF only needs two counts: how many documents there are (N) and how many of them contain the word (n). NFCorpus has 3,633 documents. In their text field:

WordDocuments containing it (n)IDF
of3,623 of 3,6330.0029
artificial205.18
sweeteners115.76
neurobiology–not in this document

"of" is in almost every document, so its IDF is almost zero and it barely affects the score. "sweeteners" is in only 11 documents, so it counts for a lot. Putting the numbers for "sweeteners" into the IDF formula: ln(1 + (3,633 − 11 + 0.5) ÷ (11 + 0.5)) = 5.7557.

The word "neurobiology" is in the question but not in this document, so it adds nothing here. BM25 only rewards words that match.

TF: repeating a word helps, less each time

TF looks at how often the word appears, with less extra credit for each repeat. With the default k1 = 1.2, a word appearing twice counts about 1.4 times as much as appearing once, not twice as much. The table shows this, worked out from the formula for a document of average length:

With a small k1 the credit runs out almost at once: ten appearances count less than 1.5 times one. With a large k1, repeats keep adding more. k1 = 0 would ignore repeats completely, and only "is the word there or not" would matter.

TF, continued: long documents get a small penalty

TF also compares the document's length with the average length of that field. With b = 0.75, a word appearing once in a document twice as long as average counts 0.71 times as much as in an average-length document. In a document half the average length it counts 1.26 times as much.

Our document's text is 152 terms long, shorter than the NFCorpus average of 228, so its words count a little extra. Its title is 6 terms against an average of 13. Length here means the number of terms the analyzer produced.

Putting the numbers for "sweeteners" in the text into the TF formula, with k1 = 1.2 and b = 0.75 (so 1 − b = 0.25): TF = 4 × 2.2 ÷ (4 + 1.2 × (0.25 + 0.75 × 152 ÷ 227.6)) = 1.796.

Putting 28.64 together

Each (field, word) score is IDF × TF. For "sweeteners" in the text, 5.7557 × 1.796 = 10.33. Here is every piece, from OpenSearch's explain API:

If you run OpenSearch's explain API yourself, it shows TF in two pieces: k1 + 1 = 2.2, which it labels "boost", and the rest, labelled "tf" (0.8162 for "sweeteners" in the text). Multiply them to get TF as written here.

The title and the text are scored separately, and IDF is counted per field. "sweeteners" appears in the title of only 1 document, this one, so in the title it has the highest IDF of all (7.79).

Last, the two fields are combined the way the search asked for: the better field counts in full and the other counts half. That is 19.10 + 0.5 × 19.08 = 28.64. The half comes from the query's tie_breaker: 0.5 setting, which gives a document some credit for matching in a second field without letting the two fields add up in full.

How much k1 and b matter

The defaults, k1 = 1.2 and b = 0.75, are rules of thumb. To see how much they matter, we need many questions and a way to score the answers.

We used three public test sets from the BEIR benchmark: NFCorpus (nutrition and medical research), SciFact (scientific claims and research abstracts) and FiQA (finance questions and forum answers). That is 1,271 questions, and for each one the test set marks which documents are relevant. To score a list of results we use nDCG@10, a number from 0 to 1 for how good the top 10 is. A relevant document near the very top counts for more than one in 9th place. Higher is better, and 1 would be a perfect top 10.

We tried every combination of seven k1 values and six b values on all three. OpenSearch applies k1 and b when it searches, not when it indexes, so each combination only needed the index reopened, not rebuilt.

Here is NFCorpus with the english analyzer. The grey outline marks the default (k1 1.2, b 0.75) and the green outline the best combination.

Most of the grid is close to the default, and the low scores are at the edges. The top row, k1 = 0, ignores how often a word appears, and every b gives the same 0.297, because with nothing to adjust, length makes no difference either. The first column, b = 0, ignores document length.

The table shows two things:

  • The defaults are close to the best.The best combination beat the defaults by at most 0.005. With stemming on FiQA, the default was the best combination.
  • The extremes cost a lot, most of all on FiQA.With the standard analyzer, FiQA's worst setting scored 0.132, against 0.241 for its best. FiQA documents are forum answers of uneven length: a tenth are 44 words or shorter, a tenth are 270 or longer, and the longest has 2,973. With b = 0 and k1 = 3, length is ignored while repeats count for a lot, and nDCG@10 falls to 0.132. NFCorpus and SciFact abstracts are more even in length, and their worst settings cost much less.

Tuning k1 and b won us little on these datasets. Knowing what they do still helps you avoid the settings that hurt, such as k1 = 0, or b = 0 on documents of very different lengths.

What made the bigger difference

The analyzer mattered more. Keeping OpenSearch's default k1 and b and only switching from the standard to the english analyzer:

DatasetstandardenglishChangeQuestions better / same / worse

Stemming improved the average on all three datasets. Question by question it is closer: on FiQA it helped 148 questions and hurt 139. "Are Avocados Good for You?" went from 0.00 to 0.58. Two of its six relevant papers only ever say "avocado", which the standard analyzer cannot match to the question's "avocados". "Freelancer: Should I start a second bank account?" went from 0.00 to 1.00. It can also go the other way: "Is Caffeinated Tea Really Dehydrating?" fell from 0.35 to 0.07.

Matching the BEIR paper's numbers

The paper that introduced BEIR also reports BM25 scores for these test sets. OpenSearch out of the box, with the standard analyzer and default settings, comes in a little lower. The BEIR paper used Anserini, a search toolkit built on Lucene, with k1 = 0.9 and b = 0.4. The paper calls these "the default Lucene parameters", but they are Anserini's defaults; Lucene's own defaults are 1.2 and 0.75. Anserini also stems English words by default (its indexer's -stemmer option defaults to Porter). Matching both gives:

NFCorpus0.3250.3070.3250.327
SciFact0.6650.6560.6810.691
FiQA0.2360.2390.2360.254

BEIR paper: Table 2, BM25 column. Ours: this lab, OpenSearch 2.19.1.

NFCorpus and FiQA now match the paper to three decimals. SciFact comes out higher than the paper. We have not tracked down why; Anserini and OpenSearch still differ in details such as their stop-word lists and exactly how the title and text scores are combined. The last column shows that OpenSearch's defaults with the english analyzer beat the paper's published BM25 on all three datasets.

In code

Both choices are index settings in OpenSearch. This is the index the lab builds, with the english analyzer and BEIR's k1 and b:

PUT /nfcorpus
{
  "settings": {
    "index": {
      "similarity": { "default": { "type": "BM25", "k1": 0.9, "b": 0.4 } }
    }
  },
  "mappings": {
    "properties": {
      "title": { "type": "text", "analyzer": "english" },
      "text":  { "type": "text", "analyzer": "english" }
    }
  }
}

Changing the analyzer means re-indexing, because the stored terms change. Changing k1 or b does not: close the index, update index.similarity.default, and open it again. To see how any score was reached, send the same query to /nfcorpus/_explain/<document id>. That is where every number in section 07 came from.
